# Bengaluru Air Quality Intelligence System

*Turning air-quality data into actionable insights.*

A full-stack analytics app: upload OpenCity air-quality files → a Pandas pipeline cleans them transparently →
cleaned records go into a relational database → **every number on the dashboard comes from a SQL query**
(CTEs, joins, subqueries, `RANK`/`DENSE_RANK`/`LAG`/`LEAD`) → a React dashboard explores them.

| Layer | Stack |
|---|---|
| Frontend | React 18, TypeScript, Tailwind CSS 4, Framer Motion, Recharts, Leaflet + OpenStreetMap, Lucide |
| Backend | Python, FastAPI, SQLAlchemy 2, Pydantic, Pandas |
| Database | MySQL 8 (production target) or SQLite (zero-setup default) — same code, switch with `DATABASE_URL` |

## Quick start

```bash
# 1. backend  (http://127.0.0.1:8000, docs at /docs)
cd backend
pip install -r requirements.txt
cp ../.env.example ../.env            # optional - defaults to a local SQLite file
python -m uvicorn app.main:app --port 8000

# 2. frontend (http://localhost:5173)
cd frontend
npm install
npm run dev
```

Then open <http://localhost:5173>. With an empty database every page shows a friendly empty state with two options:

* **Upload an OpenCity CSV/Excel file** on *Data Quality* (this is the real path), or
* **Load labelled DEMO data** — a synthetic sample (≈106k rows, 9 Bengaluru station names, 2021–2024) generated by
  `backend/app/pipeline/demo_data.py` and pushed through the *same* pipeline. Takes about a minute. It is flagged
  `is_demo`, shown with a **DEMO DATA** banner everywhere, and **never mixed** with real records (separate stations,
  separate dataset switch; once real data exists the app defaults to it).

For a single-process deployment run `npm run build` in `frontend/`; the API then also serves `frontend/dist`.

### Using MySQL

```bash
mysql -u root -p < db/migrations/001_init_mysql.sql        # optional; tables are also auto-created
# .env
DATABASE_URL=mysql+pymysql://aqi_user:change_me@localhost:3306/aqi_bengaluru?charset=utf8mb4
```

> **Honest status:** MySQL was not installed on the machine this was built on. The SQL is written in the portable
> subset of MySQL 8 / SQLite (CTEs, window functions, `CASE`, standard aggregates — no dialect-specific date
> functions, because year/month/hour/weekday are stored as columns) and the full test-suite passes on SQLite, but the
> MySQL path has **not** been run against a live server.

## What's in the app

| Page | Purpose |
|---|---|
| Landing | Product story, animated hero (real stations when data exists, otherwise a labelled illustration) |
| Overview | 6 KPI cards with animated counters and period-over-period change, monthly timeline (click → drill-down), AQI category mix, generated insights |
| Area Ranking | `RANK()`/`DENSE_RANK()` station ranking vs city average, search, sort, server-side pagination |
| Historical Trends | `LAG`/`LEAD` year-over-year change, improving/deteriorating flags (±2 % band), multi-station comparison |
| Monthly & Hourly | Seasonality, year×month heatmap, peak hours, weekday pattern, weekday×hour grid, most-polluted days/months |
| Pollutants | PM2.5 / PM10 / NO₂ / SO₂ — only columns that exist in the data are shown; histogram, monthly trend, station comparison |
| Pollution Map | Leaflet markers coloured by AQI category, popups with latest reading, pollutants and 24-month mini-chart |
| Data Quality | Upload + processing report, before/after charts, station-wise missing-data heatmap, duplicates, row outcomes, import history |
| SQL Explorer | Every analytical query with explanation, syntax-highlighted SQL, bound parameters and a live result preview |

Global filters (year, month, stations, date range) are applied by each page to every chart *and* sent to the API,
which builds a parameterised `WHERE` clause. Each page's filter bar shows only the filters that make sense for it
(e.g. the Trends page doesn't offer a year filter, because it compares years). Every table has CSV export; charts
drill into the underlying readings.

Insights ("Peenya recorded the highest average AQI…") are generated in `backend/app/insights.py` from query results.

## Data pipeline (`backend/app/pipeline/cleaning.py`)

1. Validate extension and detect columns by header pattern (e.g. `PM2.5 (µg/m³)`, `Date`+`Time` or one timestamp, `Station`, `Latitude`…).
   Wide format only; a file needs a date column and at least one of AQI/PM2.5/PM10/NO₂/SO₂.
2. Parse timestamps (ISO first, then day-first Indian formats); invalid / implausible ones are rejected **and counted**.
3. Convert readings to numbers. Blank/`NA` → NULL. Sentinels (`-999`…), non-numeric text and out-of-range values → NULL **and counted**. Missing is never turned into zero.
4. Exact duplicates removed; same station+timestamp with different values keeps the first and is counted as *conflicting*.
5. Sub-hourly rows are averaged into hourly means; daily-only files are flagged and hourly analysis is disabled for them.
6. AQI is only **derived** (CPCB max sub-index, ≥3 pollutants incl. a PM) when the source reports none, and those rows carry `aqi_derived = 1`. Reported AQI is never overwritten.
7. Stored in `air_quality_readings`; `UNIQUE(station_id, ts)` plus a file SHA-256 check make repeat imports idempotent.

**Nothing is silently dropped.** Every uploaded row is kept in `raw_records` (original JSON + its terminal status and reason),
and the report proves `original = cleaned + merged + duplicates + conflicts + bad timestamps + empty rows`.
Station coordinates come only from `Latitude`/`Longitude` columns in the data; otherwise the map says geospatial data is incomplete.

## Layout

```
backend/app/
  main.py  config.py  database.py  models.py  deps.py  insights.py
  pipeline/        cleaning.py (pure Pandas) · ingest.py (persist) · demo_data.py
  sql_analytics/   queries.py (all SQL + registry) · scope.py (filters → bound WHERE)
  routers/         dashboard · air_quality · data_quality · data · sql_explorer
backend/tests/     pipeline unit tests + API tests (run: cd backend && python -m pytest)
frontend/src/      pages/ components/ hooks/ context/ lib/
db/                migrations/001_init_mysql.sql · sample_queries.sql
```

Pre-existing scaffolding in `sql/`, `src/`, `config.yaml` (an earlier, separate pipeline sketch) was left untouched.

## API

Interactive docs at `/docs`. Main endpoints — all accept `dataset=auto|real|demo`, `year`, `month`, `station_id` (repeatable), `date_from`, `date_to`:

`GET /api/dashboard/overview` · `/api/air-quality/{stations,rankings,trends/yearly,trends/monthly,trends/hourly,pollutants,map,readings}` ·
`/api/data-quality/summary` · `POST /api/data/upload` · `GET /api/data/imports` · `POST|DELETE /api/data/demo` · `GET /api/sql/queries[/{id}]`

## Known limitations

* Long-format files (one row per pollutant) are not supported yet — a clear 422 explains what's expected.
* Uploads are processed synchronously (limit `MAX_UPLOAD_MB`, default 50); a large file means a wait of tens of seconds.
* Dashboards query the live tables; for millions of rows add pre-aggregated summary tables.
* AQI derived from instantaneous readings uses CPCB 24-hour breakpoints as an approximation — flagged, not reported-grade.
* OpenCity's real file layouts were not available while building, so column detection was tested against the demo file and synthetic variants only; adjust `HEADER_PATTERNS` in `cleaning.py` if a real file's headers aren't recognised.
